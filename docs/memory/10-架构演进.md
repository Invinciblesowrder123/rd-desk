# 架构演进

记五个阶段。前三段是被推翻的方案，留着是因为**每个都被推翻过**，
不写下来下次还会想当然地走一遍。

---

## 阶段 0：云端工作台

最早这套东西是挂在云文档平台上的：一个 HTML 页面 + 四张云端数据表
（研发项目 / 项目节点 / 每日报工 / 每周复盘），页面通过平台注入的 SDK 读写。

能用，甚至不算难用。但两个问题无解：

- **网络到不了**。使用环境是受管制的内网，短链域名直接不通，只能开编辑态。
- **数据在别人机器上**。表是云端表，导出要靠页面自己写导出逻辑。

于是有了本地版。

---

## 阶段 1：纯 localStorage 单文件

把页面改成自带一个存储适配层，数据全塞浏览器 localStorage，
双击 HTML 就能用，彻底不依赖网络。

**这一步解决了"能用"，制造了新问题**：数据在浏览器里，Python 进程读不到。
飞书机器人想查项目进度，无路可走。而且清浏览器缓存就没了。

---

## 阶段 2：页面推快照 → 服务端存 JSON / SQLite

为了解决"机器要读数据"，加了一条单向推送：页面每次写操作后，把整份数据
POST 给本地服务，服务落成 JSON（后来又改成落 SQLite 方便查询）。

当时以为这就够了：页面照旧用 localStorage（快、离线可用），服务端有个可查的副本。

**实测发现是陷阱**：

> 推一份只含 1 个项目的数据，库里原来 10 个项目被整批抹掉。

因为同步是"全量替换"，最后推送的那一份就是全部真相。
两个浏览器同时用，谁最后保存谁覆盖别人。**"热同步"只在单人单机成立。**

另外还有一层根本问题：localStorage 不是数据库。没有表结构、没有索引、
不能跨进程、不能 join。所谓"同步数据库"，当时根本没有数据库可同步。

---

## 阶段 3：服务端库成为真身（当前）

反过来做：**数据真身在服务端 SQLite，页面通过 HTTP API 读写它**。
浏览器不再自己存数据。

```
页面 ──/api──▶ server.py ──▶ bridge/desk.db
```

关键实现细节：

- 存储层用 `records(database_id, record_id, seq, data JSON)`，**整行存 JSON**，
  加字段零迁移；需要 SQL 查询的地方靠四个视图（`v_projects` / `v_nodes` / ...）补。
- 写操作按记录粒度（增/改/删单条），不是整份覆盖——多人改不同项目互不影响。
- 全局 `rev` 版本号，每写一次 +1；页面每 3 秒轮询，变了就重新拉数据。
  **跨端刷新延迟约 3 秒，这是唯一的代价，换来不再互相覆盖。**
- 前端适配层换了一个文件（`08_remotedb.js`），接口形状与之前的云端 SDK 完全一致，
  **页面业务代码一行没改**。

代价（已确认接受）：

- 服务不跑，页面就是空的（原来 localStorage 能离线看）。
- 每次操作多一次本地 HTTP 往返，实测毫秒级，无感。

留了 `legacy.html` 作为应急：自带一份数据快照，纯 localStorage，不落库。

---

## 阶段 4：飞书机器人只读接入

机器人（另一个项目）要回答问题，但它有自己的库和一套读工具。

两条路：换它的数据源（重写半个 bot），或者把中台数据镜像进它的库。

选了镜像：每轮对话前把中台的当前状态覆盖进 bot 的库，跑完调 bot 自己的
预警重算。**读路径一行不用改，写路径全部拦死。**

镜像的幂等靠中台的 `rev`：没变就跳过。

---

## 现在长什么样

```
                       ┌─ 只读镜像 ──▶ pmbot（飞书，可选）
                       │
浏览器 ──/api──▶ server.py ──▶ bridge/desk.db
                              （唯一真身）
```

一条数据线，一个写入口（页面 / API），其余全是读者。
