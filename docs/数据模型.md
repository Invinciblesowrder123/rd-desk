# 数据模型

一句话：**所有数据在一个 SQLite 文件里**（默认 `bridge/desk.db`），
分三层看——物理表、逻辑表、视图。

---

## 1. 物理层：两张表

```sql
records (
    database_id TEXT,   -- 哪张逻辑表（见 §2）
    record_id   TEXT,   -- 记录主键，20 位随机串
    seq         INTEGER,-- 插入顺序，用于稳定分页
    data        TEXT,   -- 整行 JSON（字段名就是中文列名）
    updated_at  TEXT,
    PRIMARY KEY (database_id, record_id)
)

meta (k TEXT PRIMARY KEY, v TEXT)   -- 只存一个 rev：全局版本号
```

为什么整行存 JSON 而不是一列一字段：这套表的字段是长期演进的（今天加"客户"、
明天加"节点状态"），JSON 存法让**加字段零迁移**。代价是不能直接 `WHERE 某列`，
用视图补（见 §3）。数据量在千级，性能不是问题。

`seq` 是分页游标的基础——`record_id` 是随机串，不能拿来排序。
`rev` 每写一次 +1，页面轮询它感知"别人改了数据"。

## 2. 逻辑表：四张，用固定 id 区分

| 逻辑表 | database_id | 说明 |
|---|---|---|
| 研发项目 | `XurtLd3EYpe29VppV0z0TJ` | 项目台账 |
| 项目节点 | `1urnMOWB0VL3RL0pNiNILG` | 节点（进度的核心） |
| 每日报工 | `bI9MkKD1Zvp1UwmmY6UvfX` | 每天投入 |
| 每周复盘 | `nG1nopjeQW93K0wclTs4jR` | 周会纪要 |

**项目节点.项目ID 存的是项目的 `record_id`**（20 位随机串），不是项目编码。
页面之所以能关联，全靠这一列。

## 3. 视图：给 SQL 和外部程序用

```sql
v_projects   record_id, code, name, customer, owner, stage, due_date,
             block_item, plan, note
v_nodes      record_id, project_id, name, seq, plan_date, done, done_date,
             status, owner, note
v_logs       record_id, project_id, project, log_date, qty, minutes, backfill, note
v_reviews    record_id, week, keep, problem, try_it, next_plan
```

写两条常用查询：

```sql
-- 逾期未完成的节点
SELECT p.code, p.name, n.name, n.plan_date, n.owner
FROM v_nodes n JOIN v_projects p ON p.record_id = n.project_id
WHERE n.done = 0 AND n.plan_date <> '' AND n.plan_date < date('now')
ORDER BY n.plan_date;

-- 各项目完成率
SELECT p.code, p.name, COUNT(n.record_id) AS total, SUM(n.done) AS done
FROM v_projects p LEFT JOIN v_nodes n ON n.project_id = p.record_id
GROUP BY p.record_id ORDER BY p.code;
```

> 视图用的是 `json_extract(data, '$."字段名"')`。中文键在 JSON 路径里必须写成
> `$."项目名"` 这种带引号的形式。

## 4. 字段约定

### 研发项目

| 字段 | 类型 | 约定 |
|---|---|---|
| 项目编码 | text | `PRJ-2026-001`，**业务唯一键**，跨系统对账靠它 |
| 项目名 | text | 格式固定 `客户 项目名`（单空格），如 `星河 智能咖啡机` |
| 客户 | text | 简称即可 |
| 负责人 | text | 多人用顿号分隔 |
| 阶段 | select | 概念 / 设计 / 手板 / 试产 / 量产 |
| 立项日期 | date | `YYYY-MM-DD` |
| 截止日 | date | **所有时间判断的锚点；留空 = 这个项目永不告警** |
| 单位 / 总量 | text / number | 选填，不参与进度计算 |
| 配色 | text | 卡片主色，`#RRGGBB` |
| 阻塞项 | text | 真的卡住了、需要决策的事。**不是"逾期了"** |
| 预案 | text | 阻塞发生时的应对方案 |
| 项目备注 | text | 会议纪要原文，只追加不改写 |

### 项目节点

| 字段 | 类型 | 约定 |
|---|---|---|
| 项目ID | text | 父项目的 record_id |
| 节点名 | text | 如 `EV 手板组装`、`3C 认证送样` |
| 序号 | number | 显示顺序，按计划完成日排序生成 |
| 计划完成日 | date | 逾期判断依据 |
| 已完成 | checkbox | 勾上就不再参与逾期计算 |
| 完成日 | date | 实际完成 |
| 节点状态 | select | 待开始 / 进行中 / 已完成 / 阻塞 |
| 负责人 / 备注 | text | 备注里不要写状态，状态归「节点状态」 |

节点状态四值刻意对齐了 pmbot 的 `pending / doing / done / blocked`，两边可直接对映。

### 报工 / 复盘

报工：`项目ID`、`项目名称`、`日期`、`完成量`、`工时分钟`、`补记`、`备注`。
工时存分钟，页面按 0.5 天步进显示（一天按 480 分钟）。
`项目名称` 是**建记录那一刻的快照**，不是引用——改项目名不会改历史报工。

复盘：`周标识`（本周周一的日期，如 `2026-10-26`）、`保持`、`问题`、`尝试`、`下周预案`。

## 5. 种子数据格式

`data/seed.demo.json` / `data/seed.json` 是同一个格式，首次启动（库为空时）灌进去：

```json
{
  "projects": [
    { "_id": "p1", "项目编码": "PRJ-2026-101", "项目名": "星河 智能咖啡机",
      "客户": "星河", "负责人": "张明", "阶段": "手板",
      "截止日": "2026-11-10T00:00:00Z", "配色": "#6366f1",
      "阻塞项": "", "预案": "", "项目备注": "" }
  ],
  "nodes": [
    { "_id": "n1", "项目ID": "p1", "节点名": "EV 手板组装", "序号": 1,
      "计划完成日": "2026-10-28T00:00:00Z", "已完成": true,
      "完成日": "2026-10-29T00:00:00Z", "节点状态": "已完成", "负责人": "张明", "备注": "" }
  ],
  "logs": [],
  "reviews": []
}
```

要点：

- `_id` 是种子内的临时主键，灌库时会重新生成；`nodes[].项目ID` 指向项目的 `_id`。
- 日期可以是 `2026-11-10` 或 `2026-11-10T00:00:00Z`，页面只取前 10 位。
- 灌种子**只在库为空时发生一次**。想重新灌：删掉 `bridge/desk.db` 再启动。

## 6. API 速查

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/rev` | 版本号 + `index.html` 构建戳 `build`，页面轮询用 |
| GET | `/api/db/<id>/records?cursor=&size=` | 分页取记录 |
| POST | `/api/db/<id>/records` | 新增，body `{"properties": {...}}` |
| POST | `/api/db/<id>/records/<rid>/update` | 局部更新（只传要改的字段） |
| POST | `/api/db/<id>/records/<rid>/delete` | 删除 |
| POST | `/api/db/<id>/batch` | **原子批量写**，body `{"ops": [{op, databaseId, properties|recordId}]}`，单事务 |
| GET | `/api/db/<id>/schema` | 字段定义 |
| GET | `/api/export` | 整库导出 `{projects,nodes,logs,reviews}` |
| POST | `/api/shutdown` | 优雅退出：回响应 → checkpoint → 关连接 → 退进程 |

复合动作（例如"完成节点"＝置节点完成 + 记一条报工）必须走 `/api/batch`，
不要在前端发两次独立请求——两次请求可能一个成功一个失败，留下半成功的脏状态。
展开细节见 [memory/30-踩坑与约束.md](memory/30-踩坑与约束.md) 第 15 条。

写入时的字段值用 oneof 包装：`{"text": "..."}`、`{"number": 1}`、`{"date": "..."}`、
`{"checkbox": true}`、`{"select": "选项文本"}`。
